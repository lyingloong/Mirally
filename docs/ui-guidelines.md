# Mirally UI 设计与审查规范

2026-10-28。适用于编码 Agent 与人工维护者，执行入口为根 [AGENTS.md](../AGENTS.md) 的“界面与交互约束”。这些是结合产品问题制定的项目规则，不是将某个网站的风格整体移植到 Mirally。以下案例是审查结论和改造方向，不代表页面已经调整。

## 为什么不能只规定“删掉说明文字”

用户指出的聊天区说明暴露出两个问题：权限的有效状态与会话开关不一致；低频设置、状态和教程挤在同一任务区域。单纯删字，会留下同样难懂的控件；把整段搬进 tooltip，只是隐藏问题。

判断顺序应是：用户现在要做什么 → 功能的状态和作用域是否清楚 → 控件是否合适 → 标签是否自明 → 是否仍有必须说明的后果。最后才考虑加一条短提示。必要的审批对象、风险、不可逆影响、输入要求和恢复操作仍须让用户在决策时看见。

## 本仓库案例

| 现象 | 问题 | 后续设计应满足的条件 |
| --- | --- | --- |
| 全局自动批准已开启，同时展示未勾选的“本会话自动批准”，再解释关闭无效 | UI 把偏好值当成实际生效状态，迫使用户理解两个配置的叠加关系 | 聊天入口呈现一个真实的有效权限状态；来源/作用域按需查看，编辑入口与实际可改变的行为一致。是否支持会话覆盖必须由产品权限模型明确，不能直接画出尚不存在的覆盖选项 |
| 每次聊天都看到“重启后失效、微信独立约束”等整段说明 | 少数设置场景的知识占据高频聊天区域 | 有效范围在权限选择处清楚表达；手机授权放在相关渠道设置。确实影响当前决定的后果在决定时出现 |
| “计划模式”后常驻一句教程，旁边并列“压缩上下文” | 任务模式和低频维护动作缺乏层次 | 模式有稳定名称与明确选择；若等待下一轮生效，用短状态说明待应用，而非伪装立即生效；压缩放入会话工具入口，避免每次输入都占一行 |
| 新增一个能力就新增一条设置栏或一张介绍卡 | 按实现清单铺界面，而非按用户任务组织 | 先决定能力何时被使用、在哪里能被找到，再复用相应入口；不要把所有能力都设成常驻控件 |

这些案例不授权移除能力、削弱审批或改写权限语义。UI 重构应同时保持真实能力、状态、可发现性和可访问性。

## 每次交付前的审查

1. **目标与入口**：用户无需先读教程，就能辨认当前任务及下一步；常用操作直接可达，低频操作有清晰入口。不是“所有东西都折叠起来”。
2. **文案减法**：逐条检查说明是否只重复标签、解释实现或罗列例外。先删冗余，再查删后不清楚的交互；必要短提示放在所属控件旁，背景知识放帮助。不能靠缩小、变灰或藏进 tooltip 假装精简。
3. **状态演练**：分别检查默认、继承、覆盖、加载、待保存/下轮应用、失败和撤销；用户看到的状态须能预测下一次操作。按钮点击、偏好写入、服务端确认和实际效果分别有据可查。
4. **操作连续**：完成一次主要任务并尝试失败重试、切会话或返回页面，检查数据归属、焦点、草稿和滚动。页面没有异常日志并不证明流程正确。
5. **呈现与可访问性**：检查实际渲染、长内容、相关窄屏/窗口形态、键盘和浮层边界。图标按钮有名称和点击空间，信息不只靠颜色/悬浮呈现。检查减少动态效果，避免闪烁和目标位移。

检查范围随改动选择；简单文案调整不要求重跑全产品或制造只匹配字符串的测试，权限、异步和跨会话交互则需要相应行为验证。交接说明查了什么及未覆盖什么，不以“美观、现代、简洁”代替证据。无需为执行这些规则额外向用户请求批准。

## 调研依据与取舍

查阅日期：2026-10-28。下列链接是依据，不要求每次 UI 修改重新抓取网页；项目约束以当前 AGENTS.md 为准。

| 来源 | 采用的原则 | 在 Mirally 的落点 |
| --- | --- | --- |
| [GOV.UK：Designing good questions](https://www.gov.uk/service-manual/design/designing-good-questions) | 先改善问题和结构，不能用帮助文案修补复杂的基础界面；必要帮助仍有价值 | 默认不加解释；若基础操作仍难懂，回到命名、控件和功能模型 |
| [DWP：Hint text](https://design-system.dwp.gov.uk/guidance/hint-text) | 说明有具体用户需求才加，聚焦眼前问题，不承担整个服务的教程 | 不把权限规则、生命周期和渠道限制塞进一个控件的描述槽；英文标点细则不照搬 |
| [GOV.UK：Details](https://design-system.service.gov.uk/components/details/) | 只将部分用户需要的内容按需展开，不藏多数用户必须的信息 | 背景帮助与决策必需信息分层；不把重要后果统统藏起来 |
| [NN/g：Progressive disclosure](https://www.nngroup.com/articles/progressive-disclosure/) | 优先呈现核心选择，按需提供高级能力 | 主任务不被高级控制和维护操作占满；次级入口仍须可发现 |
| [Fluent 2：Switch](https://fluent2.microsoft.design/components/web/react/core/switch/usage) | 开关表达明确二元设置和立即变更，标签简短稳定；提交式选择和不确定状态使用其他组件 | 不用互相覆盖的开关模拟权限模式；待应用状态应如实呈现 |
| [GOV.UK：Button](https://design-system.service.gov.uk/components/button/) | 过多同等强调的行动入口会削弱主操作 | 按任务区域建立主次；不是规定整页只能有一个按钮 |
| [Vercel：Web Interface Guidelines](https://github.com/vercel-labs/web-interface-guidelines) | 为编码 Agent 提供可核对的交互、布局、动效、语义和状态检查，而非抽象审美口号 | 复用组件、检查真实内容/焦点/异步及减少动效；不照搬其品牌配色、英文 Title Case 等偏好，也不把其中所有建议作为普遍标准 |
| [W3C：Content on Hover or Focus](https://www.w3.org/WAI/WCAG22/Understanding/content-on-hover-or-focus.html) | 自定义悬浮信息应可关闭、可悬停阅读并保持可读 | 提示须支持焦点/触屏替代并正确布局；不被侧栏裁剪。该说明页解释 WCAG 条款，不是新的认证声明 |
| [W3C：Target Size (Minimum)](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html) | 控件点击目标需要足够尺寸或间距，标准存在明确例外 | 项目通常至少按 24×24 CSS px 设计点击区域，触屏优先更大；不要把缩小按钮当作减少视觉噪声的方法 |

这里对“有效权限状态”“临时授权入口”“低频维护操作位置”的要求，是根据这些来源和本仓库实际问题作出的设计判断，不宣称是上游逐字规定。
