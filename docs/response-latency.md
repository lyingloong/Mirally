# 响应耗时定位与模型配置修正

## 2026-10-15：发送前的「正在准备本次对话」

这是 OpenClaw 的 `preparing_context` 阶段，包含模型和认证解析、工具准备及上下文组装。最近两次真实请求从发送确认到提交模型约 6.8–6.9 秒；一次更慢请求还记录了 11.37 秒会话数据库写队列等待，不能把这些时间都算成模型服务延迟。

原来的日常工作目录位于开发仓库内，OpenClaw 将它识别成整个代码项目，系统提示准备会额外查询项目记忆。该检索 worker 空闲 60 秒后退出，间隔一段时间发送消息又会付启动成本。新初始化改用用户数据目录中的独立 workspace；本次本机修正完整复制旧 workspace 后，仅通过官方配置补丁更改 `agents.defaults.workspace`。原目录保留，模型、工具、活动记忆设置和会话数据库不变，不需要重置会话。

配置热加载不会清除旧会话进程内的项目集合；本机已在后台空闲时通过 Mirally 的完整重启流程更换 Gateway 进程，确认新路径生效并保留持久会话。Windows 上原生 RPC 重启可能只重建服务而保持进程，不足以保证清除这份缓存。

安装版 OpenClaw 的隔离对照使用同样配置和本地模拟模型，仅改变 workspace 是否位于 Git 仓库内；未调用付费模型或执行工具。Memory disabled 与当前缺失 YAML 的默认一致。

| 系统提示准备 | 仓库内 | 仓库外 |
| --- | ---: | ---: |
| 首轮 | 2,290 ms | 11.6 ms |
| 连续第二轮 | 21.7 ms | 7.2 ms |
| 间隔 60 秒第三轮 | 1,632 ms | 6.1 ms |

第三轮整个原生调度从 4,159 ms 降至 2,293 ms，工具、技能和 Git baseline 阶段都只有约 1–12 ms。此对照有 55 项工具，真实界面记录为 71 项，不能把对照总耗时当成实际对话首字时间；首次加载工具与模型服务响应仍有额外等待。本机证据为 `.artifacts/turn-preparation-probe/strict-vs-temp.json`，临时进程均已关闭。

## 2026-10-04：模型线路与思考参数

2026-10-04 在本机 OpenClaw `2026.9.6`、`mirally/qwen/qwen3.8-flash` 中转线路下验证。分别记录发送确认、原生准备、模型生成和工具执行；发送确认只证明请求被接收，不代表任务已经完成。

## 慢请求的主要原因

最初双材料办公请求约 160 秒才开始工具执行，约 302 秒完成首轮。原生日志和只读运行轨迹显示：

- 第一次模型流准备完成后，约 123.5 秒返回 `Provider returned an incomplete or malformed tool call`，没有超时或主动中止标记。
- 该轮输出恰好达到默认 8,192 token 上限，其中中转报告 6,337 个思考 token；原生运行设置却是 `thinkLevel: off`。
- 原生执行了一次安全重试。重新准备后，首个成功模型调用约 17.7 秒；成功重试整轮仍报告 7,616 个思考 token。

当时自定义模型只有名称和 ID，没有声明推理能力或参数兼容方式。原生以非推理模型处理，关闭思考没有转换成中转实际需要的参数，中转仍使用自己的默认思考行为。输出达到上限与工具调用错误同时出现，强烈指向思考占用输出预算后导致调用不完整；SDK 已删除无效参数，不能进一步断言具体截断位置。这不是已确认的网络超时，缩短超时或直接降低输出上限不能解决该问题。

## 已完成的修正

通过原生模型配置修正当前线路，并将元数据保留在公开初始化模板中：

```json
{
  "reasoning": true,
  "compat": {
    "thinkingFormat": "openai",
    "supportsReasoningEffort": true,
    "supportedReasoningEfforts": ["none", "low", "medium", "xhigh"],
    "reasoningEffortMap": { "minimal": "low", "high": "xhigh" }
  }
}
```

默认 `thinkingDefault` 明确设为 `off`，保留此前的默认选择。`reasoning: true` 声明模型具备可配置的推理能力，不代表强制开启思考。原生请求将 `off` 转为 `reasoning_effort: none`，`low` 保留为 `low`，`high` 转为该模型的 `xhigh`；用户仍可按任务选择思考档位。

同一中转的流式测试接受 `none`、`low` 和 `xhigh`，`none` 未返回思考文本。原生 direct、managed 两条请求构建路径均有回归测试，输出预算没有降低。中转参数不能推广到其他未知模型；初始化匹配已知模板模型时保留元数据，未知模型继续使用通用配置，已有私有配置不会被初始化脚本覆盖。

浮窗发送时立即安排状态刷新，然后等待原生发送确认，减少状态更新对后续事件的依赖。办公草稿明确整理本次消息的材料，并将交接标题说明为回复排版，减少模型误解为需要查找的流程。没有增加请求代理、额外模型调用、任务调度或缓存系统，也没有修改 OpenClaw 包源码。

## 实际复测

同一 Gateway 的独立合成会话中，修正前后分别发送相同请求，计时从 `chat.send` 开始。办公任务读取同样两份材料并生成一份真实汇报。

| 请求 | 修正前 | 修正后 |
| --- | ---: | ---: |
| 新会话首次短问答 | 16.55 秒 | 16.58 秒 |
| 同会话立即追问 | 4.94 秒 | 3.70 秒 |
| 双材料汇报 | 41.94 秒 | 32.08 秒 |
| 办公任务开始首个工具 | 4.96 秒 | 5.11 秒 |

上述六次原生请求的发送确认在 12～203 毫秒，均完成，没有无效工具调用、工具失败或超时；两份汇报均独立回读并核对待确认、预算、时间与负责人。修正前轨迹报告思考 token，修正后三次没有该字段；缺失不冒充显式零计数，实际中转 `none` 测试另证实关闭思考的行为。

这些是单次复测，模型输出长度与缓存命中有所不同，不能宣称固定百分比提速。约 302 秒的旧请求还包括两份产物、回读和补充，与本表的一份汇报并非相同负载。

另通过实际浮窗重复“双附件 → 两份文件 → 给老师版补充”流程：

| 档位与草稿 | 原生首轮 | 原生补充轮 | 观察 |
| --- | ---: | ---: | --- |
| 映射后的 off，原草稿 | 约 113 秒 | 约 119 秒 | 搜索安装目录，补充轮重复列目录 9 次 |
| 原草稿，单会话 low 对照 | 约 131 秒 | 约 63 秒 | 工具降至 5+4 次，思考仍有 4,360+2,361 token |
| 默认 off，明确本次材料与回复格式 | 约 55 秒 | 约 45 秒 | 没有目录查询循环；仍有少量工具错误后自行修正 |

最后一轮从提交到原生状态显示完成约 119 秒，包括冷准备和两个串行回合；连同文件预览和截图约 122 秒。17 项实际检查全部通过，核对两份附件中的独立标记、补充标题、小样本限制、材料分歧、真实文件、交接与固定按钮。`low` 没有设成全局默认，所有原生档位入口仍保留。此对照包含草稿和素材标记变化，属于诊断与功能复验，不是严格性能基准。

这次第一条发送确认约 102 毫秒；紧接着在原生冷准备期间发送补充，确认约 4.04 秒，其中原生服务端约 4.00 秒。即时界面反馈不等于服务端总能在百毫秒内确认，后者仍有冷准备成本。

## 剩余耗时

新会话首次问答仍有约 13 秒原生准备时间，模型配置修正尚未消除这部分成本。一条实际阶段日志记录 `system-prompt: 5382ms`、总准备 `6628ms`；其余准备时间发生在这段之前。紧接着的同会话追问明显更快。

只读隔离测量中，记忆查询 worker 冷启动约 1.24 秒、连续调用约 48 毫秒。原生运行模块首次加载也有数秒成本，重复加载接近零。这些说明原生冷加载需要继续分析，不能把整个十三秒全部归因于记忆、数据库锁或某个模块。没有为追求速度关闭记忆、删除工具、缩短上下文或改变原生重试机制。

验收时分别观察新开会话第一条、同会话追问、读取文件和较长交付，记录发送确认、首个可见回复/工具与完成时间。若分钟级等待再次出现，应先按运行 ID 查原生轨迹的思考 token、输出上限与失败重试，避免把所有等待都算成界面卡顿。

最后的双文件流程中，累计 20 轮模型调用区间约 96 秒，工具处理合计约 1 秒；剩余等待主要是模型生成与原生准备。测试里的补充发生在提交后约一秒、原生模型回合尚未启动时；此时原生没有可注入目标，会排为后续回合。发送 ACK 中的输入 ID 不必等于后续实际模型运行 ID，不能把它当作运行中调整已采用的证明。真正活跃任务中的 steer 仍以此前独立后台工具验收为依据。

## 计时依据与证据

`assistant.timestamp` 是 SDK 创建输出、准备模型请求的时刻，不能当作首 token 时间。`recordTimestampMs` 是记录进入历史的时刻，也不能当作用户发送时间。原办公补充消息的创建时间在初始请求后 5.68 秒，较晚写入历史并不说明发送较晚；运行中补充的可靠验收仍以实际发送、接收确认和最终文件为依据。

本机证据在 Git 忽略的 `output/openclaw-native-verification/latency/`：`trace-timing.json`、`gateway-timing.json` 记录旧请求失败及重试；`provider-probe*.json` 记录中转流式测试；`native-baseline.json`、`native-mapped.json` 和 `native-trace-comparison.json` 记录原生对比；`office-clear/verification.json` 与 `office-clear-trace.json` 记录最终实际窗口及运行轨迹，`office-low-trace.json` 记录低思考对照；`checks-*.json` 核对文件，`config-mapping.json` 只记录修改字段。公开文档和模板不含实际密钥、Gateway 令牌或私人会话。
