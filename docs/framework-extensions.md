# Mirally 扩展接口与组合设计

状态：重构接口草案 v0.4，2026-10-22。用户已明确采用同仓 DSH 源码内核并允许直接修改 API、loop、Session、宿主与 UI；本文产品扩展契约仍须实现和验收。Profile/Bundle/Slots 可选复用，不再限制必须通过外部插件接入。当前 OpenClaw 是迁移基线；源码导入不代表新宿主已运行。实施见[重构计划](framework-refactor-plan.md)，来源见[内核说明](../kernel/README.md)与[上游记录](../kernel/dsh/UPSTREAM.md)；UFO 子模块仍只读，私有配置保留。

目标是让新来源、服务、交互入口、模型、策略和执行器能通过明确接口加入产品。扩展机制从第一版进入结构；接口数量和具体形状随真实接入验证演进。内置实现也使用对应的公开契约，避免外部扩展永远处于能力不足的第二条路径。

## 1. 三种边界

| 概念 | 职责 | 示例 |
| --- | --- | --- |
| 普通模块 | 实现一个领域内部的规则与数据操作；通过正常函数/对象协作 | 记忆冲突判断、候选去重、报告格式整理 |
| 接入接口 / 扩展点 | 由责任领域定义输入、输出、调用时机和保证，容纳一种可替换或可组合能力 | 情境检索、投递渠道、执行器、界面位置 |
| Extension | 一个可配置、声明依赖和兼容范围、管理资源生命周期的集成单元，可贡献多个接口实现 | 日历集成同时提供事件来源、检索、提醒触发与卡片 |

一个产品集成可以横跨多个领域，但各领域仍拥有自己的权威状态。Extension 不等于一个模型 Agent、进程、数据库或商店安装包；一个包也不要求只贡献一个工具。

产品域接口由 Mirally 定义。可直接修改 `kernel/dsh/` 的服务注册、工具、MCP、加载器与客户端来落实这些贡献；也可复用既有 Profile/Bundle/Slots，不强制全部内置代码先变成外部插件。以同一个内核宿主的依赖和生命周期为基础，不再建设另一套通用插件运行时。侵入式开发不取消领域边界，产品内部仍无需处处引用 DSH 的 ctx。

## 2. 首批应验证的扩展面

这是接入地图，不是封闭的全局枚举。每一类接口由对应领域拥有，不统一成 `Plugin.execute(any)`。

| 扩展面 | 主要契约 | 组合与权威归属 |
| --- | --- | --- |
| 来源 Source | 来源身份、发现/启停、变化或观察、游标、时间/质量/缺口、撤销与引用解析 | 多来源并存；Activity 或相应领域接纳数据。发现与注册不启动采集 |
| 情境与记忆处理 | 有预算的 query、带来源/版本/时效的结果；整理器提交有依据的候选 | 多检索器可组合，由 Context 选择与裁剪；Memory owner 决定写入、冲突和撤回 |
| Skill provider | 技能目录与元数据、按需正文、相对资源解析、依赖能力与调用映射 | 指导当前任务的流程知识；通过宿主 Skill 机制加载，不作为长期个人记忆，也不等同于单个工具 |
| 能力与执行器 | 明确请求/结果 schema、实际效果、操作身份、状态/回执、超时和真实取消能力 | 注册工具或委派适配；同一逻辑能力的实现由显式路由选择，实际效果在能力内部核验 |
| 投递 Channel | 可用性、内容与附件支持、提交身份、送达/回复回执及可核对程度 | 多渠道并存，产品选择投递策略；不把渠道回调当用户同意 |
| 界面 Surface / UI | 产品视图、可用位置、输入命令与交互状态 | 共享权威会话和业务状态；页面、卡片、伙伴入口等通过明确插槽组合 |
| 触发与策略 | 变化触发、机会候选、时机建议或附加限制，携带理由与有效期 | 领域定义合并/优先级；不能绕过显式设置、预算与效果检查 |
| 模型及其他 Provider | 路由与能力声明、输入/输出、用量和错误 | 复用或直接修改内核 provider 机制；产品声明需要的模态/结构化输出等能力，避免另建第二套驱动 |
| 可替换领域服务或后端 | 所属领域的完整行为契约、状态/schema 版本与迁移方式 | 同一权威职责显式选一个实现；替换 Memory 后端需保留版本、来源、墓碑与作业语义，不能只替换 search |

接口的组合方式也属于契约：来源和渠道可以多选；检索结果需合并裁剪；有权威状态的后端不能靠“最后注册者覆盖”；安全和授权限制只能收紧。候选排序等软策略可以有确定的顺序或被明确选中的实现，不能让插件自行提高优先级就夺取决定权。

新增接入若属于现有扩展点，只注册实现与配置。确实出现新的领域能力时，由该领域增加命名、版本化的 typed 扩展点，通过显式依赖暴露给其他扩展；不修改一个不断增长的核心 switch，也不提前为未知需求创建空接口。产品语义改变则通过明确的契约演进处理。

## 3. 最小公共结构

下面只是表达设计的 TypeScript 草图，不是已经存在的 SDK，也不限制 Python 或进程外实现的语言。

```ts
interface ExtensionManifest {
  id: string;                 // 稳定、带命名空间的身份
  version: string;
  apiRange: string;
  requires: ServiceRequirement[];
  optional: ServiceRequirement[];
  requestedAccess: AccessDeclaration[];
}

interface MirallyExtension {
  manifest: ExtensionManifest;
  setup(registration: RegistrationScope): void | Promise<void>;
}

interface RegistrationScope {
  services: DeclaredServices; // 仅声明且公开的领域接口
  contribute<T>(point: ExtensionPoint<T>, value: T): Registration;
  onDispose(cleanup: () => void | Promise<void>): void;
}
```

`ExtensionPoint<T>` 由所属领域导出，说明稳定身份、契约版本、校验和组合方式；配置或进程外边界同时需要可验证的序列化 schema。编译期类型和运行时校验共同工作，不能只写一个 TypeScript interface 就认为跨进程兼容。同仓内核中可以直接实现或调整注册入口，不需要先在上游可用接口之外叠一套管理器；普通私有方法不因此成为公共扩展 API。

`setup` 只在一个受控装配阶段注册贡献和清理；提交成功后才开放调用。它不偷偷启动采集、调用付费模型或产生外部动作。注册返回句柄，以便反注册与撤销资源；功能是否启用及何时开始工作由配置与领域生命周期决定。`onDispose` 表达资源清理责任，实际停止、排空和失败状态遵循下一节，不能用一个回调掩盖它们。

跨进程适配要保留同样的来源、身份和效果语义。每个接口按需要携带请求身份、目标会话代、来源版本、超时/取消、范围和预算；不为所有廉价纯函数强制传一份巨大的全局上下文。插件只能请求领域修改，不能直接改别的模块数据库或复制一套个人画像。

数据交换使用明确方法；确需订阅时发送有类型的领域事实。视图重放不产生新动作，不把任意事件广播当全部模块的调用协议。

## 4. 生命周期、兼容与退出

1. **装配前检查。** 检查接口版本、必需服务、配置与能力；未知必需扩展点、重复身份、独占冲突和缺必需依赖时拒绝激活并说明原因。可选依赖缺失只影响声明的可选能力，不能默默降级授权或假装支持取消/恢复。装配失败撤销已暂存的注册并清理已分配资源。
2. **受控启用。** 装配成功后开放贡献。数据源按已启用范围开始工作，后台模型仍受统一预算；配置声明 requestedAccess 不自动授予权限。
3. **停用先关准入。** 阻止新调用和触发，按依赖关系先关闭依赖方或受影响能力，再排空提供方；取消或排空在途工作、解除订阅并释放资源。迟到事实回执仍保留，迟到计划不能继续执行。无法确认停止时报告未知并保持禁止新效果。
4. **状态有归属。** 扩展自有同步游标、设置和作业可使用命名空间存储及 schema 版本；已进入 Memory、承诺或原生 Session 的内容依然由原 owner 管。停用不自动删除这些内容，注销来源后保留不可用说明和历史引用。
5. **替换与升级显式发生。** 固定版本组合，检查依赖方与数据迁移；有权威状态的实现先停写再迁移再绑定新实现。代码回滚不等于外部动作或数据迁移可撤销，失败时保留可核对的状态。
6. **重启是允许的选择。** 首版不承诺任意热插拔；需要重启的扩展明确显示。重复启停不重复注册、遗留 timer 或保留隐形 writer。

超时、取消、错误与重试各接口具体定义：区分不可用、拒绝、过期、冲突、可重试失败与效果未知，保留必要的具体原因；收到 AbortSignal 不等于外部效果已撤销，未知结果不自动重试，不支持恢复的执行器就声明不支持。故障影响尽量局限到该能力及其依赖；进程隔离只在平台、资源独占或故障影响值得时增加。

同进程插件是受信代码，注册权限声明不形成安全沙箱。实际数据和工具 guard 仍由产品能力边界落实；需要接入不受信代码时再选择受控进程或远端适配，不把安装等同于授予全部本机访问。

## 5. 用实际新增接入检查接口

| 接入 | 通过现有机制贡献什么 | 核心应保持稳定的部分 |
| --- | --- | --- |
| 日历服务 | 有稳定事件 ID/版本的来源、只读日程检索、关注变化触发、可选创建事件能力与日程卡片 | 事件出现不自动成为用户承诺；提醒仍由一个产品 owner 管，写日历走明确能力与回执 |
| 手机或语音入口 | Surface 输入、Channel 送达/回复、会话与命令身份映射；需要时单独增加来源 | 身份、Memory、Conversation 和纠正/停止语义共用；断线重试不创建第二份聊天真相 |
| 外部自动化执行器 | 请求 schema、能力声明、状态/效果回执、能支持的取消/核对，以及 UI 状态展示 | 复用本次帮助范围与授权，不假装所有执行器都能暂停/无损恢复；本机桌面仍按资源归属独占 |
| 另一种检索或存储 | 检索器可先作为 Context 来源；真要替换 Memory 后端时实现完整 owner 契约并迁移 | 不把“接入一个搜索服务”误认为已替换 Memory 的版本、纠正、撤回和作业保证 |

例如日历集成是一个 Extension 对多个 typed 接口的组合。新增它应主要增加集成实现和装配配置；不要求另建日历人格、重写接纳调度器，或为了 UI 卡片改动模型循环。

## 6. 设计验收

- 内置与外部实现可通过相同扩展契约接入，内置实现也遵守该扩展点的校验与生命周期；领域内部私有方法不自动变成公共 API。
- 两个同类来源/渠道可同时工作；独占实现冲突会明确拒绝或要求配置选择，结果与加载顺序无关。
- 一个跨领域扩展可以同时提供来源、检索、动作和 UI，并共享其身份、配置与生命周期。
- 停用或升级后不留重复 timer、writer、订阅与已失效入口；已发生效果和历史来源可追溯。
- 一个新扩展点可由明确的领域所有者导出，不把核心 registry 写死为目前几种产品功能。
- Python、MCP 和宿主插件只改变适配，不削弱来源、范围、取消、效果和版本语义；不能保留语义时说明能力缺口。

先验证内置实现、日历式跨领域接入和一个进程外执行器的契约。扩展市场、通用沙箱、复杂依赖解析与任意热更新可以后做；公共接入边界、依赖声明、组合规则和退出责任应从第一版存在。

## 7. Skill、MCP 与现有插件生态

三者是第一版需要明确设计和验收的兼容面。保留各自的格式或协议，通过适配接入 Mirally；独立 Skill 与 MCP server 无需先重写为 Mirally 插件。一个 Extension 也可同时打包或声明它们，并贡献产品服务与 UI。

| 兼容面 | 接入方式 | 在系统中的位置 |
| --- | --- | --- |
| Agent Skills | 读取标准 SKILL.md 及附属资源，提供发现、按需加载、用户调用与能力检查 | Skill provider → 宿主 Skill 机制/当前任务情境；脚本另走执行能力 |
| MCP server | 本地 stdio、远端 Streamable HTTP；按双方版本与能力处理工具、资源和提示模板 | 工具 → 具体能力接口；资源/资源模板 → 来源读取与 Context；prompts → 可调用模板目录 |
| Mirally / 宿主插件 | 声明兼容版本、依赖、配置与贡献，按生命周期装配 | 贡献 Skill provider、MCP 配置、能力、策略、服务与 UI 等 |

### 7.1 Skill 兼容

Agent Skills 的基本包包含带 name/description 元数据的 SKILL.md，可附 scripts、references、assets；支持渐进加载。方案保留原目录结构和相对引用：先索引元数据，选用后加载正文，所需资源再读取，不把全部技能正文放入每轮请求。[Agent Skills 格式规范](https://agentskills.io/specification)

Skill provider 只负责目录、读取与调用映射，不另建模型循环。复用内核 Skill 注册/加载机制，必要时直接修改其命名、选择与调用行为；按来源+名称建立产品身份，保留内容版本和原始路径。同名技能可明确绑定或选择，不因目录扫描顺序静默覆盖。配置目录基于项目/用户配置解析，不硬编码开发机路径；资源解析校验规范化路径，包外材料通过相应受控读取能力取得。

区分“可发现”“可读取说明/资源”“可运行所需步骤”。正文提到 Python、shell、外部服务或工具，并不说明这些能力已经可用；可支持脚本的 Skill 通过明确配置的脚本执行能力接入，声明解释器、依赖、材料范围和效果，使用现有范围、预算、取消与回执机制。默认不开放通用 shell 与支持 Skill 不冲突，但受控脚本入口必须列为实际兼容能力验证；缺能力时说明部分支持或不可用。

脚本执行边界需真实可落实；同用户进程若不能限制读取/网络，就不能把配置声明当隔离保证。Skill 的 allowed-tools 等宿主相关字段按能力解释，不自动扩大产品授权；未知字段保留或明确诊断，不能冒充所有宿主方言都已兼容。Skill 说明与外部资料保留各自来源，不自动成为最高优先级产品规则。

### 7.2 MCP 兼容

兼容范围分别声明 tools、resources/resource templates、prompts，及协商支持的其他能力，不用一个“支持 MCP”开关包办。MCP 的三个基本服务能力及本地/远端传输见[官方架构说明](https://modelcontextprotocol.io/docs/2026-07-28/learn/architecture)。实际协议版本与能力按连接结果记录；不承诺未测试的全部扩展、长任务恢复或媒体格式。

连接适配管理配置、必要认证、进程/连接生命周期、发现、命名、超时、断连和停用。列出已配置连接与启动协议发现分开；协议发现可能启动本地 server，不能冒充纯读文件。Mirally 自有 Activity/Memory server 的启动和发现仍不启动采集。远端 server 的行为按其实际能力和部署方式验收。

工具保留 server-qualified 身份、schema 和原始结果；资源保留 URI、来源与可用版本，按需读取并进入 Context；prompts 作为可发现/显式调用的模板，并保留出处，不将所有模板自动注入。被调用工具仍通过效果检查，server 的自述或 annotations 不代替授权。连接重建不等于可重做未确认的远端动作。

导入基线 DSH rc.2 已有 stdio/Streamable HTTP、工具桥和共享资源读取；其文档明确 **MCP prompt templates 尚不支持**。可直接补内核 MCP 服务与客户端调用面，不必等待官方扩展或在外部绕接；补齐并测试前仍标注不支持。媒体、认证、可选协议能力逐项核对，不能把源码可修改当作功能已实现。[导入基线 MCP client](https://github.com/deepseek-ai/deepseek-harness/blob/dsh-v0.2.1-rc.2/packages/mcp/mcp-client/README.md)

除消费外部 MCP server，Mirally 也可按需把明确的只读查询或受控能力提供为 MCP server，沿用相同 owner 和范围；不为双向接入复制数据真相。当前已有 Activity/Memory MCP 资产优先复用，扩大导出范围属于后续显式设计。

### 7.3 插件兼容与组合

Mirally 产品贡献采用本文契约；同仓内核可直接改变插件服务和客户端接口，相关原生插件需随本地 API/内核修订验收。记录上游基线不等于维持上游全部插件的二进制或源码兼容；包版本、依赖与兼容声明必须反映实际测试。其他宿主即使同名“plugin”，其 manifest、hook、服务 API 和 UI 也可能不同；按格式适配并列明范围，不承诺任意包直接互装。

例如一个报告扩展可以携带报告 Skill、声明一个资料 MCP server，并提供产物卡片：Skill 指导流程，MCP 提供数据/操作，文件能力产生结果，UI 展示原产物引用。它们共用已有会话、来源、预算和停止范围；单独的 Skill 或 server 也能被配置使用。

兼容检查分为 Skill 格式/宿主方言、MCP 协议/能力、插件宿主/产品 API 版本，不能只看一个包版本。控制已启用目录与模型可见工具，避免技能正文和全部 MCP schema 无界进入每轮请求；导入基线 MCP 桥的已注册工具会进入请求，可以直接修改发现/可见性机制降低成本，但必须实际测量和验证，而非假设已有按需加载。

停用撤销所属注册、目录暴露、连接重连与新执行，共享依赖按归属保留。已加载进原生 Session 的说明或模板不会随目录卸载消失，依照来源失效/必要会话交接处理；在途脚本或远端效果无法确认停止时保留未知状态。

验收至少覆盖：纯说明 Skill、引用资源/带脚本 Skill、本地与远端 MCP 的工具/资源/prompts，以及同时贡献 Skill+MCP+UI 的扩展；分别显示支持、部分支持和不支持。以上是目标兼容契约，本轮未安装技能、连接新 server、执行脚本或改变正式运行链路。
