## 2026-10-03 交互方向补充

按用户最新要求，工作台执行时平滑收至屏幕侧边，展示必要状态；靠近后展开，可在任务进行中输入补充。用户不必先手动暂停：内部自动协调桌面输入权，发送后使旧计划失效并重新观察。浮窗保持清晰、不透明，优先使用经过实际截图链路验证的原生捕获排除；半透明不能替代截图隔离。

产品同时引入可查看、可清空、重启可恢复的会话记忆，让后续任务参考之前的要求和结果。长期个人偏好记忆作为后续独立能力。最新实现与验证范围见 [桌面体验实现说明](desktop-experience-implementation.md)。以下原则继续适用，早期建议的手动暂停交互可以由等效的自动输入协调取代。

## 文档定位

本文档是 Mirally 前端体验的目标与规划建议，用于说明要解决的问题、必要能力、安全边界和基本验收方向。它不是固定的产品规格、视觉稿或实现方案；项目曾使用 OpenAssist 名称，代码包仍保留 `openassist`。

开发者可以根据技术验证、用户体验和项目现状，重新设计界面形态、交互流程、视觉表现与技术实现。如果开发过程中形成了更合理的方案，可以调整或覆盖本文建议，但应说明调整理由，并确保核心目标、安全要求和验收标准得到满足。

以下内容可以自由调整：

- 界面形态、布局和视觉风格。
- 组件组织和状态呈现方式。
- 动效、提示方式和交互细节。
- 前端技术栈和进程架构。
- 本文列出的具体功能组合和实现顺序。

以下目标原则上必须满足：

- 前端不能污染 Agent 用于决策的桌面截图。
- 前端不能干扰 Agent 的鼠标、键盘、焦点和窗口操作。
- 用户能够了解 Agent 当前状态及是否需要介入。
- 用户能够可靠地暂停、停止或接管任务。
- 敏感操作必须经过用户确认。
- 前端或通信异常时，Agent 不能继续无监督执行。

## 产品目标

前端应提供低干扰、反馈及时、上下文连续的沟通体验。可以参考游戏聊天系统和远程控制软件的体验，但不限定具体布局或窗口形式。

用户应能够：

- 提交任务并在执行过程中补充信息。
- 了解 Agent 当前正在做什么、是否仍在运行以及是否需要介入。
- 回答 Agent 的追问并处理敏感操作确认。
- 暂停、继续、停止或人工接管任务。
- 查看任务结果和必要的执行记录。
- 配置界面行为、状态反馈和 Agent 接管提示。
- 在后续版本中使用语音输入任务。

## 设计原则

### 不干扰 Agent

界面体验不能以牺牲桌面观察准确性和操作可靠性为代价。任何显示在桌面上的前端内容，包括窗口、提示、描边和动画，都必须纳入截图与输入隔离设计。

### 状态透明

用户应能快速判断 Agent 是否正在运行，当前处于观察、规划、操作还是验证阶段，以及是否正在等待用户处理。

### 用户拥有最终控制权

用户应始终能够暂停、停止或接管任务。紧急停止能力不应依赖复杂的界面路径，也不应因当前应用占据焦点而失效。

### 展示可理解的信息

前端可以展示任务状态、操作摘要和结果，不应展示模型内部推理、隐藏提示词或未经整理的原始响应。调试信息可以通过独立的诊断入口提供。

### 允许方案演进

本文中的界面、动效、设置和协议均可被更好的方案替换。变更应以核心目标和可验证结果为依据。

## 状态与信息

前端与 Agent 应共享结构化状态，避免前端通过分析日志文本猜测运行状态。建议至少覆盖以下语义：

| 状态 | 用户需要了解的信息 |
| --- | --- |
| 空闲 | 可以提交新任务 |
| 准备中 | 正在初始化任务或运行环境 |
| 观察中 | 正在获取桌面状态 |
| 规划中 | 正在决定下一步操作 |
| 执行中 | 正在操作的应用和动作摘要 |
| 验证中 | 正在检查操作结果 |
| 等待用户 | 需要用户补充信息 |
| 等待确认 | 存在需要确认的敏感操作 |
| 已暂停 | 暂停原因和恢复入口 |
| 人工接管 | Agent 已停止操作，由用户控制 |
| 已完成 | 任务结果摘要 |
| 失败 | 失败位置、原因和可恢复操作 |
| 已停止 | 任务由用户或系统终止 |

状态名称、数量和视觉表达可以调整，但语义应清晰且可由前端稳定消费。

执行期间可以展示：

- 当前任务摘要。
- 当前操作的应用或窗口。
- 当前动作及最近完成动作的用户可理解摘要。
- 当前是在等待模型、工具还是应用响应。
- 已执行步骤、运行时间以及是否需要用户介入。
- 暂停、停止和人工接管入口。

合适的动作摘要类似“正在 Word 中填写文档标题”或“正在等待浏览器加载结果”。不应直接向普通用户展示完整动作 JSON、模型原始响应或 Chain-of-thought。

## 截图隔离

### 基本判断

透明度、鼠标穿透、降低窗口层级或移动窗口位置，都不能单独保证前端不进入 Agent 截图。透明窗口通常仍可能被桌面捕获；鼠标穿透只解决输入冲突。

截图隔离应作为前端与 Agent 之间的明确协议，而不是单纯的视觉样式。

### 建议策略

可以采用多层保护：

1. 优先验证 Windows 原生窗口捕获排除能力，例如 `WDA_EXCLUDEFROMCAPTURE`。
2. Agent 截图前通知前端进入截图保护状态。
3. 原生排除不可用或验证失败时，临时隐藏所有相关前端窗口和视觉效果。
4. 确认窗口状态已经生效后再执行截图。
5. 截图完成后恢复前端状态。
6. 隔离失败时暂停 Agent，不使用受污染的截图继续决策。

原生捕获排除、截图时隐藏或其他方案都只是候选实现。最终方案必须根据 Mirally 实际使用的捕获链路进行验证。

建议提供等价于以下语义的协调事件：

- 截图即将开始。
- 前端已进入可安全截图状态。
- 截图已经完成。
- 截图隔离失败。

具体接口名称和通信方式由实现者决定。关键要求是过程可确认、可超时、可失败，不能只依赖未经验证的固定延迟。

## 输入与焦点隔离

Agent 执行期间，前端不得意外抢占键盘焦点、拦截鼠标点击或改变目标应用的窗口状态。鼠标穿透、隐藏窗口或其他机制可以作为实现手段。

需要用户输入时，建议遵循以下语义流程：

1. Agent 停止发出新的桌面操作并进入暂停状态。
2. 前端恢复可交互状态。
3. 用户输入、确认、拒绝或选择人工接管。
4. 前端明确结束本次交互。
5. Agent 重新观察桌面后再继续任务，不能直接沿用交互前的旧截图和坐标。

## Agent 接管视觉反馈

前端可以提供类似远程控制软件的视觉反馈，让用户持续知道电脑当前是否由 Agent 控制。可探索的形式包括：

- 屏幕边缘动态描边或呼吸效果。
- 活动窗口轮廓。
- 不同运行状态对应的颜色变化。
- 简短的操作提示。
- 接管开始和结束动画。
- 可选的状态提示音。

这些形式仅是设计方向，不是实现要求。最终方案应由开发者根据整体体验决定。

所有接管反馈必须满足：

- 不进入 Agent 截图。
- 不遮挡真实应用内容或改变桌面可操作区域。
- 不拦截鼠标和键盘。
- Agent 停止、异常退出或用户接管后及时消失。
- 无法保证截图隔离时自动关闭。
- 支持减少动态效果等辅助功能设置。

执行、等待用户、暂停、敏感确认、人工接管和异常状态应具有足够清晰的区别，但不要求采用固定颜色或动效。

## 用户控制

前端至少应支持以下能力：

- 提交任务和补充信息。
- 确认或拒绝敏感操作。
- 暂停、继续和停止任务。
- 切换到人工接管状态。
- 查看任务结果及必要的执行记录。

建议提供不依赖当前窗口焦点的紧急停止方式。具体采用全局快捷键、系统托盘入口或其他方式，由开发者判断。

停止操作具有最高优先级，应尽快阻止新的模型动作、连续动作和工具调用。无法立即中断的外部操作应明确显示“正在停止”，避免用户误以为控制已经结束。

## 敏感操作确认

确认信息至少应包括：

- Agent 准备执行的操作。
- 操作对象。
- 可能产生的影响。
- 允许、拒绝和人工接管入口。

确认期间 Agent 必须暂停。前端断开、确认超时或发生异常时，不能默认允许高风险操作。

## 前端设置建议

设置结构和具体选项可以重新设计，建议至少考虑以下方面。

### 界面行为

- 置顶、自动展开、自动收起或自动隐藏策略。
- 是否显示操作摘要和详细执行记录。
- 任务完成后是否主动展示结果。
- 全屏应用中的界面行为。

### 接管反馈

- 是否启用接管特效。
- 特效形式、强度、速度和透明度。
- 不同状态的视觉反馈。
- 是否播放提示音。
- 是否在全屏应用中自动关闭特效。

### 截图保护

- 当前使用的隔离策略和可用状态。
- 原生捕获排除是否验证成功。
- 是否已经回退到截图时隐藏。

截图隔离失败时停止任务属于安全要求，不建议作为可关闭设置。

### 辅助功能

- 减少动态效果。
- 高对比度和色盲友好状态表达。
- 字体大小。
- 键盘操作支持。
- 提示音音量。

### 语音输入

- 是否启用语音入口。
- 输入设备和识别语言。
- 按住说话或点击开始/结束录音。
- 识别后直接提交或先编辑。

语音识别默认建议采用“识别后先编辑”，避免识别错误直接触发电脑操作。具体流程可由开发者重新设计。

## 异常与恢复

设计应覆盖以下场景：

- 前端进程或 Agent 进程异常退出。
- 前端与 Agent 通信中断。
- 截图隔离失败或 Windows 捕获排除不可用。
- 多显示器、DPI、分辨率或主显示器发生变化。
- 目标应用失去响应。
- Agent 停止请求未及时生效。
- 接管视觉效果未正常清理。

建议采用失效安全原则：

- 前端断开后暂停新的 Agent 操作。
- 确认通道不可用时拒绝敏感操作。
- 截图隔离失败时停止观察和执行。
- 恢复连接后重新观察桌面，不直接继续旧计划。
- 残留的前端窗口和接管效果能够被检测和清理。

## 前端与 Agent 的接口方向

不限制通信技术，但建议传递结构化事件，而不是让前端依赖 Python 日志作为主要数据源。事件语义可以包括：

- 任务创建、开始、完成、失败和停止。
- Agent 状态变化。
- 当前应用与动作摘要。
- 动作开始、完成和失败。
- 截图保护开始、就绪、结束和失败。
- 用户输入请求和敏感操作确认请求。
- 暂停、继续、停止和人工接管。
- 前端连接状态、错误和恢复信息。

接口应考虑事件顺序、任务标识、重复事件、断线重连和停止请求的优先级。具体协议可以在实现阶段另行设计。

## 验收方向

前端方案至少应验证：

- Agent 使用的截图中不存在 Mirally 前端内容。
- 界面和视觉效果不会影响控件检测、视觉定位和点击坐标。
- Agent 执行期间不会意外拦截鼠标、键盘或焦点。
- 用户能够快速判断 Agent 当前状态以及是否需要介入。
- 用户能够可靠地暂停、停止或接管任务。
- 敏感操作未经确认不会执行。
- 用户交互结束后，Agent 会重新观察桌面。
- 前端异常或通信中断时，Agent 不会继续无监督执行。
- 接管效果可以配置、关闭，并遵守辅助功能设置。
- 常见 DPI、分辨率、全屏应用和多显示器环境得到验证。
- 截图隔离失败可以被检测，并能阻止 Agent 继续执行。
- 本地凭据、模型内部推理和不适合展示的原始数据不会出现在普通界面记录中。

验收应尽量包含自动化截图和状态测试，不能只依赖人工观察。

## 建议的实施优先级

1. 建立前端与 Agent 的结构化状态及控制接口。
2. 完成并验证截图、鼠标、键盘和焦点隔离。
3. 实现基础任务输入、状态反馈、追问和确认流程。
4. 实现暂停、停止、恢复和人工接管。
5. 加入可配置的接管视觉反馈。
6. 完善设置、辅助功能、异常恢复和诊断能力。
7. 接入现有语音识别 Provider，并完成录音交互。

该顺序只是建议。负责开发的 Agent 可以根据技术风险和更优方案重新排序。

## 非本期强制范围

以下能力可以继续规划，但不要求首个完善版本全部实现：

- 运行日志检索和跨会话长期记忆（基础历史会话管理已实现）。
- 跨设备同步。
- 多 Agent 可视化编排。
- 语音输出。
- 远程控制。
- 插件市场。
- 独立账户系统。
- 高级主题系统。

本阶段更重要的是建立可靠的截图与输入隔离、清晰的 Agent 状态反馈、可信的用户控制，以及可扩展的前端与 Agent 接口。
