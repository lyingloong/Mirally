## 0. 用户原始需求

### 0.1 原始表述

> **整理**（第 1 轮，`user-request`）：项目 XXX 报销额度 3000，已报 160、1800 两笔；希望 Mirally 记住并在被问到时回答还剩多少；隔很久再问也要有理有据。
>
> **逐字要点**（用户明确约束）：**「不能用传统记忆/向量检索」**；应由**模型维护设计好的结构化存储**，并**规定协议**。

> **整理**（第 2 轮澄清，`user-request`）：**报销只是例子**。真正想要的是**像记事本一样的长期存储**：随手记下事件、小想法、见闻；**模型可以按需建目录**来组织；隔很久再问仍然找得回、说得清。同一约束仍然成立：**不用传统记忆/向量检索**，由模型维护结构化存储并遵守协议。

### 0.2 从表述中提炼的产品意图（需求师归纳，非原话）

1. **长期**：内容要活得过会话、活得过记忆预算与语义整理；一周、一年后仍能取回。
2. **随手**：用户不会先建表结构再说事；记录必须是**一句话就能存**。
3. **可组织**：内容变多以后需要目录/分类，但目录应当**由模型在需要时创建**，而不是强迫用户预先设计。
4. **可信**：隔久再问要“有理有据”——能说明依据是哪条记录、什么时候写的、有没有被改过。
5. **可计算**：某些记录（报销、预算、计数）需要**确定性汇总**，不能靠模型心算（第 1 轮例子）。
6. **不用记忆/向量检索做主路径**：记忆用于“人”，记事本用于“事与物”，两者职责不同（§9 论证）。

## 2. 目标与非目标

### 目标

1. **随手可记**：一句“记一下：今天在梅坞老巷看到一只三花猫，很亲人”即可落库，不需要用户先设计 schema。
2. **模型按需建目录**：内容变多、出现明显主题时，模型可以**主动建议或直接创建 collection**，并把后续记录归入；用户可以改名、合并、拆出。
3. **长期可查**：标签 + 时间 + 全文 + 确定性计算四条检索路径；不依赖召回相似度。
4. **可追溯**：每条记录有来源（会话/渠道/回合/原话摘要）、时间（事件时间与记录时间分开）、创建者、版本链。
5. **可外加结构**：某一类记录可以升级为**带不变量与工具的类型**（如 `ledger`），计算由工具完成，不由模型心算。
6. **不与记忆冲突**：明确“什么进记事本、什么进记忆”，并在回答中可区分。

### 非目标

- **不以记忆/向量检索作为记事本的主查询路径**（§9）；也不改造现有记忆系统。
- 不做通用笔记应用（不做富文本、附件管理、协作编辑、Markdown 渲染、导出为知识库）。
- 不做自动扫描桌面/浏览历史写入记事本（活动采集是独立能力）。
- 不做跨设备同步（Q6）。
- 不自动把每一句话都写进记事本（写入触发见 Q4）。

## 3. 可选方案

| 方案 | 做法 | 优点 | 代价/风险 | 适用条件 |
| --- | --- | --- | --- | --- |
| **A. 通用事件存储 + 按需类型（推荐）** | 统一 `entries` 表（自由文本 + 时间 + 标签 + collection），`types`/`schema` 描述某类记录的可选结构；特定类型（ledger）附带不变量与工具 | 一条写入路径覆盖想法/见闻/事件/账目；目录可演进；计算型交给工具 | 设计一个“足够通用又不万能”的模型是本提案最大风险 | 需要长期、可查、可算的用户记录 |
| B. 全部塞进记忆 | 用 `MemoryStore` 的 `user_confirmed` 记录存 | 零新表 | 会被语义整理改写、被 TTL/预算影响、无目录/无冲正/不可审计 | 不可用（用户已排除） |
| C. 偏好 JSON 存“记事本” | `preference.set("notes", [...])` | 复用 API | 16 KiB 上限、无分页/索引/审计/并发语义 | 只够几十条 |
| D. 每条一个 Markdown 文件 + 目录 | 文件系统即目录 | 用户可直接看/备份 | 索引、并发、原子性、审计都要自己做；Windows 路径与编码问题；与产品库不一致 | 已有的个人知识库工作流 |
| E. 通用 key-value/表格抽象 | 万能表格给所有场景 | 复用性 | 与 [产品方向](../../../docs/product/vision.md) 原则 1“不建立万能 PersonalState”冲突 | 出现 3+ 真实场景后再考虑 |

**结论**：A。B 被用户排除；C 只用于设置；D/E 见 Q9/Q10。

## 4. 推荐方案总览

```text
用户："记一下：老周说下周工位搬到三号楼，记得带工牌。"
   ↓
模型：notebook.entry.add(text=..., occurred_at=..., tags=["工作","搬迁"], proposed_collection="工作/搬迁")
   ↓
工具：校验（长度、时间、敏感标记）→ 写入 entries（可撤销窗口内）→ 返回 entry_id + 归类建议回执
   ↓
用户："上次老周说的搬工位那事是哪周？"
   ↓
模型：notebook.search(query="老周 搬工位", time_hint=...)  → 命中条目（含 event_time、collection、tags）
   ↓
模型：按工具返回逐条转述，不自行推断时间或补写内容
```

**职责切分（协议核心）**

| 角色 | 负责 | 不负责 |
| --- | --- | --- |
| 模型 | 判断“是否值得记”、抽取事件时间与标签、建议目录、把查询结果转述成人话、发现歧义时追问 | 不做汇总算术、不编造内容、不擅自改写已有记录 |
| 工具 | 校验、写入、幂等、版本、审计、检索、计算（仅计算型类型） | 不做语义理解、不决定是否记录 |
| 存储 | 唯一事实 | 不做跨设备合并 |

## 5. 数据、接口与协议

### 5.1 数据模型（自由记录优先，结构按需附加）

| 表 | 关键字段 | 说明 |
| --- | --- | --- |
| `notebook_collections` | `id`、`path`（如 `工作/搬迁`，**模型可建**）、`title`、`parent_id NULL`、`kind`（`user_defined`/`auto_created`）、`created_by`、`status`（`active`/`archived`）、`created_at` | 目录树；`path` 唯一；`auto_created` 表示模型建议创建（Q1 决定是否默认创建） |
| `notebook_types`（可选） | `name`（`note`/`event`/`idea`/`ledger`…）、`schema_json`、`strictness`（`free`/`soft`/`strict`）、`tools[]` | **类型只在需要时出现**；`note` 为默认类型，零约束 |
| `notebook_entries` | `id`、`collection_id NULL`、`type`（默认 `note`）、`title NULL`、`body TEXT`、`tags_json`、`event_time`（事件发生时间，可空）、`recorded_at`（写入时间）、`time_quality`（`exact`/`day`/`approx`/`unknown`）、`props_json`（类型附加结构）、`status`（`active`/`superseded`/`reversed`/`deleted`）、`supersedes_id NULL`、`source_json`、`idempotency_key UNIQUE`、`sensitivity`、`created_by`、`revision` | 一条记录 = 一句话/一个事件/一笔账 |
| `notebook_revisions` | `entry_id`、`revision`、`before_json`、`after_json`、`at`、`actor`、`reason` | 只追加的版本链（改正文/换目录/合并都留痕） |
| `notebook_audit` | `seq`、`at`、`actor`、`channel`、`conversation_id`、`turn_id`、`tool`、`request_id`、`entry_id`、`action`、`detail_json` | 写入审计（与 revisions 互补：审计记录“谁用什么工具做了什么事”） |

**时间双轨**（关键）：`event_time` 是“事情发生的时间”（“上周搬的工位”），`recorded_at` 是“我知道这件事的时间”（今天）。两者必须分开，否则“隔久再问”会答错；`time_quality` 明确记录用户说的时间粒度（精确/仅日期/约略/不明）。

**目录与条目的关系**：一条记录**可以不属于任何目录**（收件箱式默认池），也可以属于一个 collection；同一主题可先散记、后归并（`collection.move`）。

### 5.2 目录（collection）与 manifest

- **manifest**：一个 collection 可带一份可选清单 `manifest_json`，描述“这里通常记什么、有哪些字段、推荐标签”；初始为空即自由记录。
- **目录创建的三种触发**（Q1）：①用户明确说“建个目录”；②模型发现同一主题出现 ≥N 条（建议 N=3）时**建议**创建并等确认；③模型直接创建 `auto_created` 目录，事后可归档。
- **目录约束**：`path` 层级 ≤ 4，单段 ≤ 24 字；重名冲突返回候选而非自动合并；归档目录不影响其下记录的可查性。
- **不预设分类体系**：不内置“工作/生活/财务”等强制目录；模型可以建议，但用户不使用也完全可用。

### 5.3 记录类型与 schema 严格度

| 类型 | 字段 | 严格度 | 用途 |
| --- | --- | --- | --- |
| `note`（默认） | `title?`、`body`、`tags`、`event_time?` | `free` | 小想法、见闻、一句话 |
| `event` | `title`、`body`、`event_time`（必填）、`people?`、`place?` | `soft` | 发生过的具体事情 |
| `idea` | `body`、`tags`、`status?`（未成型/在试/已放弃） | `free` | 待发展的小想法 |
| `ledger`（示例，见 §6） | `account_id`、`amount_minor`、`currency`、`kind`（`expense`/`reversal`）… | `strict` | 需要可加总的记录 |

**严格度语义**：`free` 任意附加字段进 `props_json`；`soft` 缺字段只警告不影响写入；`strict` 缺字段**拒绝写入**并要求澄清。类型不能凭空把自由记录“强行升级”——升级是显式动作（`notebook.entry.retype`），旧数据保留。

### 5.4 来源、时间与标签

| 字段 | 写入来源 | 用途 |
| --- | --- | --- |
| `source.conversation_id` / `channel` / `turn_id` | 当前会话上下文 | “这条是哪次说的” |
| `source.utterance`（≤200 字摘要） | 用户原话 | 人为核对；**不存全文** |
| `created_by` | `user` / `model_inferred` | 区分用户明确说 vs 模型抽取（见 Q4） |
| `tags` | 用户显式给的 + 模型建议（建议需在回执中回显） | 检索主路径之一 |
| `event_time` + `time_quality` | 用户表述（“上周三”“大概是 9 月”） | 时间检索；不明时存 `unknown` 而非猜今天 |

### 5.5 纠正、冲正与删除

| 用户意图 | 动作 | 结果 |
| --- | --- | --- |
| “这条写错了” | `notebook.entry.revise(entry_id, patch, reason)` | 写 revision，正文更新，`status` 仍 `active` |
| “这条记重复了” | `notebook.entry.merge(keep, drop)` | 被并条目 `superseded`，指向保留条目 |
| “我不记得说过这个” | `notebook.entry.reverse(entry_id, reason)` | `reversed`，仍在审计中可查，默认检索不返回 |
| “删掉这条” | `notebook.entry.delete(entry_id, reason)` | **软删除**（Q8 决定是否提供彻底删除）；默认检索不返回 |
| “这笔记错目录了” | `notebook.entry.move(entry_id, collection_id)` | 记录 revision |
| “目录建错了” | `notebook.collection.archive(id)` | 目录归档，条目回到未归类 |

**原则**：任何改动**留痕**；不物理覆盖正文；删除的出口在 Q8 由用户决定。

### 5.6 查询

| 查询意图 | 工具 | 说明 |
| --- | --- | --- |
| 关键词/主题 | `notebook.search(query, collection?, tags?, type?, time_range?)` | 全文 + 标签过滤（具体用 `LIKE`、FTS 还是两者组合由工程按实测收敛，见 §10.3） |
| 时间窗口 | `notebook.timeline(from, to, collection?, tags?)` | “上个月我记过什么” |
| 某目录 | `notebook.collection.list(collection)` + 分页 | 目录浏览 |
| 单条 | `notebook.entry.get(entry_id)` | 含来源、版本链、敏感标记 |
| 可加总类型 | 类型的专属工具（如 `ledger.balance`，§6） | **只允许工具计算**，模型不得对 `entries` 自行加总 |
| “为什么这么答” | 上述工具返回的 `evidence[]`（entry_id、event_time、collection、excerpt） | 模型据此逐条引用 |

### 5.7 幂等

- `idempotency_key` = `hash(entry 语义：type|text 规范化|event_time|collection|source.conversation_id|source.turn_id)`。
- 同 key 同内容 → `{replayed: true, entry_id}`；同 key 不同内容 → `IDEMPOTENCY_MISMATCH`，不覆盖。
- 同一回合重试幂等；**不同回合说同一句话**（“今天很开心”）应各记一条——因此 key 必须含 `turn_id`，不能只按文本去重。
- 模型批量写入（一次说三件事）时，每条单独一个 key，部分失败不回滚已成功条目，并在回执里逐条标注。

### 5.8 敏感内容

> 第 3 轮修订（关闭 Codex P1）：**渠道不设专属默认**。用户已明确要求微信端与桌面端采用一致的能力与信任设置（PN-0069 / PN-0071）；本提案不得凭空新增“微信一律逐次确认”“私密正文在微信默认不回显”这类渠道专属方案。
> 第 5 轮修订：**Q5 已决定为 A**（规则 + 模型打标；桌面与微信一致；默认检索与导出排除）。本节承诺在 A 阶段按 §8.3 生效，**不因阶段推迟而降级**。密钥/凭据另走 §5.12。

| 项 | 方案 |
| --- | --- |
| 识别 | 写入时按规则打标（密码/证件号/银行卡/密钥形态）+ 模型可显式标 `sensitivity=private` |
| 存放 | 默认与普通记录同库，带 `sensitivity` 标记；**不进入记忆系统**的自动召回（数据 owner 边界，与渠道无关） |
| **权限** | **完全沿用既有语义**：写入走与桌面相同的 `ActionGate` 与全局持续信任；读取能力跟随当前渠道已有的会话/工具权限，**不新增渠道专属白名单或黑名单**（见 §5.10） |
| 展示 | 由**既有**的渠道呈现与隐私规则决定；本提案不新增“某渠道默认隐藏”的规则 |
| 检索 | 默认检索不含 `private`，需用户当次明确要求（与渠道无关，所有端一致） |
| 备份/导出 | **P4**：导出功能本身在 P4，届时可选“是否包含私密记录”，默认排除（A 阶段不存在导出入口，故该项不构成 A 门禁） |

**若确实需要渠道差异化**（例如未来希望在他人可及的设备上减少正文暴露），必须走 §10 的 Q5b：只能是**用户在设置中显式开启**的选项、默认关闭，并写清风险；提案阶段不预设、不实现。

### 5.9 持久化、备份与迁移

| 项 | 方案 |
| --- | --- |
| 位置 | `product.sqlite3` 新增表；**独立 `notebook.sqlite3` 作为工程备选**——由实现者在 PR 中给出理由（备份粒度、跨库一致性、WAL 增长）后定，不占用用户决策位 |
| 事务 | 单条写入一事务；跨表（条目+revision+audit）同事务 |
| 索引 | 初版建议 `(collection_id, event_time)`、`(status, recorded_at)`、`UNIQUE(idempotency_key)` 与 tags 过滤；**具体索引、是否引入 FTS（含中文 trigram）由工程按记录量实测收敛**（可参考 dev-0023 中文检索评测），不逐项让用户拍板 |
| 备份 | 产品库既有备份策略；可选 `notebook.export`（JSON/CSV，见 Q8） |
| 迁移 | 新增表用 `CREATE TABLE IF NOT EXISTS` + schema 版本递增；既有表零改动；回滚 = 保留表不读 |
| 与记忆的迁移 | **不做双向迁移**：记忆里的经历不回写进记事本，记事本里的记录也不进记忆（§9） |

### 5.10 权限与隐私

- **写入**：与桌面完全相同的 `ActionGate` 语义——逐次确认 / 本会话临时信任 / 全局持续信任三档原样适用；**不新增渠道专属审批**，也不因渠道不同而收紧或放宽（与 [产品方向](../../../docs/product/vision.md)“个性化改善行为，不扩大行动权限”与渠道文档的“微信与桌面共用同一动作审批策略”一致）。
- **读取**：跟随当前渠道既有的会话与工具权限；本提案不新增渠道级可见性规则。
- **记录文件内容为非执行型数据**：写入记事本本身不改变任何外部状态，因此**不需要**为它单独设计权限档位；审批目的在于让用户看见“它在记什么”，具体是否逐次/临时/持续由既有信任设置决定。
- **注入**：工具只返回本次查询需要的字段与 ≤300 字摘要，**不整表注入**。
- **敏感标记的 owner 是数据，不是渠道**：`sensitivity` 在 A 阶段影响默认检索（A 无导出入口），P4 导出时同样默认排除，对所有端一致；任何渠道差异化只能是用户显式开启的设置项（Q5b）。

### 5.11 工具 API（协议面）

| 工具 | 入参 | 出参 |
| --- | --- | --- |
| `notebook.entry.add` | `body`、`type?`、`title?`、`tags?`、`event_time?`、`time_quality?`、`collection?`、`props?`、`idempotency_key`、`source` | `{entry_id, collection, suggested_tags, warnings[], sensitivity}` |
| `notebook.entry.get` | `entry_id` | `{entry, revisions[], source, sensitivity}` |
| `notebook.entry.revise` | `entry_id`、`patch`、`reason` | `{entry_id, revision}` |
| `notebook.entry.reverse` / `delete` / `merge` / `move` | 见 §5.5 | `{entry_id, status, revision}` |
| `notebook.search` | `query?`、`tags?`、`collection?`、`type?`、`time_range?`、`limit` | `{entries[], evidence[], total}` |
| `notebook.timeline` | `from`、`to`、过滤条件 | 同上（按 `event_time` 排序） |
| `notebook.collection.create` / `list` / `archive` / `rename` | `path`、`manifest?` | `{collection_id, path, created_by}` |
| 类型专属 | 例：`ledger.balance`（§6） | 由类型定义 |

**写给模型的硬规则**

1. 回答“上次/之前/某天”的问题必须先 `notebook.search`/`timeline`，**不得**凭印象作答。
2. 引用记录时给出 `entry_id` 或可读摘要（“3 月 12 日记的”）。
3. 涉及汇总数字（金额、次数、天数）只有类型提供工具时才可回答，且必须用工具结果。
4. 不确定是否值得记录时，先回执“要记吗”而不是默认写入（Q7）。
5. 目录建议可以由模型提出，但不得在用户不知情时改变已有记录的归属。
6. **凭据类内容一律不进入对话上下文**：用户说“记一下，我的邮箱密码是 …”时，模型只能调用 `notebook.secret.store`，回执里只有引用与掩码；**不得**把明文复述、回显或写进任何普通记录（§5.12）。

### 5.12 密钥/敏感凭据的安全存储与取用（新增，第 5 轮）

> 动机：记事本必然会收到“帮我记住这个密码/验证码/API Key”的请求。如果只按 §5.8 打一个 `sensitivity` 标记，**明文仍然躺在 SQLite 里、仍可能被注入上下文**。密钥与普通私密记录不是同一类东西，必须单独设计。

#### 5.12.1 数据形态：明文不落库

| 层 | 内容 | 明文？ | 位置 |
| --- | --- | --- | --- |
| `notebook_secrets` 行 | `secret_id`、`label`、`collection?`、`tags`、`created_by`、`rotated_at`、`revoked_at`、`scope`、`envelope`（密文） | **否** | 与记事本同库（`product.sqlite3`），但**只有密文列** |
| `envelope` | 信封加密结果：`v1:<key_id>:<nonce/counter>:<ciphertext>`（AEAD，密钥取自 OS 密钥库） | 否 | 同上 |
| 密钥 | Windows：DPAPI（当前用户范围）保护的 kek；其他平台：系统密钥库（Keychain / Secret Service）——沿用仓库既有做法（如微信 token 与本机凭据的 DPAPI 使用） | **从不落库** | OS 密钥库 |
| 普通记事条目 | 只允许存 `secret_ref: secret_<id>` 与掩码（`••••1234`）、label | 否 | `notebook_entries`（`sensitivity=private`） |

**硬约束**

1. 明文**不得**出现在：SQLite 任意列、`notebook_audit`/`notebook_revisions`、日志、stderr、错误消息、导出文件、记忆系统、**模型上下文**（含工具入参回显与工具结果）。
2. 写入路径是**单向**的：模型只能提交“要存某个值”，由**执行层**直接接收该值并加密；模型拿到的回执是 `{secret_id, label, masked, fingerprint(前 8 位 sha256)}`，**不含明文**。
3. 读取路径默认不存在：`notebook.search` / `entry.get` / `timeline` / `collection.list` 对 `notebook_secrets` **一律不返回**解密值，只返回 `{secret_id, label, masked, locked: true}`；这些查询**不返回**密文本身。
4. 密码/验证码类内容写入时，若模型检测到用户是在“记录”而非“使用”，只建 secret，不建普通条目正文。

#### 5.12.2 取用协议：一次性 `secret.use`

```text
用户："用我那个部署 token 调一下接口"
模型：notebook.secret.list(label=…)            -> [{secret_id, masked, label}]   （无明文）
模型：notebook.secret.use(secret_id, purpose)  -> 需用户显式授权（ActionGate 逐次确认）
执行层：解密 -> 注入到 目标工具的受控字段（环境变量 / header），
        调用完成后立即清零，不写日志、不回显
模型：只收到 {status: "used", secret_id, purpose, at, target_tool, receipt_id}
```

| 规则 | 说明 |
| --- | --- |
| 一次性授权 | 每次 `secret.use` 都需要**当次**用户确认；与全局持续信任不叠加（密钥是高风险动作，见 §5.10 三档中**不使用“持续信任”档**） |
| 值不出执行层 | 解密只发生在执行层；模型、上下文、工具回执都只有引用 |
| 绑定目标 | `secret.use` 必须声明 `purpose` 与 `target_tool`，执行层只把值注入该工具的受控通道；不接受“把值打印出来看看” |
| 有效期 | 默认单次、默认 5 分钟内过期；不提供“长期驻留内存”模式 |
| 频率 | 单 secret 每分钟最多 N 次（工程收敛），超限拒绝并审计 |

#### 5.12.3 轮换、撤销、删除、审计

| 动作 | 行为 |
| --- | --- |
| 轮换 `notebook.secret.rotate` | 写入新 `envelope`，保留旧 `key_id` 记录为 `rotated_at`；**不保留旧密文可解密副本**（立即覆盖） |
| 撤销 `notebook.secret.revoke` | `revoked_at` 置位；此后 `secret.use` 立即失败；普通查询仍显示“已撤销（掩码）” |
| 删除 `notebook.secret.delete` | 强制覆盖密文列后删行（`PRAGMA secure_delete` 语义），审计留痕；若用户要求“彻底删除”而备份仍含旧值，必须如实说明（见 R5） |
| 审计 | `notebook_audit` 记录 `store/rotate/revoke/delete/use/deny`，字段只有 `secret_id`、`purpose`、`target_tool`、`at`、`actor`、`channel`、`receipt_id`；**永不记录明文、指纹以外的派生物** |
| 密钥（kek）本身 | 由 OS 提供；kek 失效（换机/换用户）时所有 secret 进入 `locked`，需用户重新录入，**不静默降级为明文** |

#### 5.12.4 泄露与失败路径（必须显式处理）

| 情形 | 行为 |
| --- | --- |
| 用户把明文贴进对话 | 立即建 secret 并**提示“已在对话中暴露，建议更换”**；不把它写进普通条目正文 |
| 模型误把明文复述 | 视为**严重缺陷**：实现必须拦截（写入前扫描 + 回执模板化），测试用负控制覆盖 |
| 解密失败（kek 变更/密文损坏） | 返回 `locked`，**不重试、不回退明文**；提示用户重新录入 |
| `secret.use` 目标工具调用失败 | 值已注入但结果未知：记录 `unknown`，**不自动重试**（避免重复副作用） |
| 未授权取用尝试 | 拒绝并审计 `deny`；连续 N 次拒绝后对该 secret 加冷却 |
| 备份/导出 | A 阶段无导出入口；P4 导出**默认不含** `notebook_secrets`，若用户显式选择包含，只导出密文（无解密能力即无价值，需在文档写明） |

#### 5.12.5 阶段归属

| 能力 | 阶段 |
| --- | --- |
| `secret.store/list/masked 查询`、明文不落库、普通查询不返回值 | **A**（A 一旦允许记录“密码/密钥形态”内容，就必须有安全落点，否则等于鼓励用户把明文写进正文） |
| `secret.use`（一次性授权 + 执行层注入 + 审计） | **A**（最小可用：能存不能用等于半个功能；且它同时验证“值不出执行层”这条核心承诺） |
| `secret.rotate/revoke/delete` | **A**（与 §8.2 的纠错一致性：能存就必须能换、能撤、能删） |
| 频率限制的精细策略、跨设备密钥同步、导出密文 | **P4/P5**（Q6b、Q8） |

## 6. 示例类型：`ledger`（报销只是它的一个用法）

> 本节说明“自由记录之上如何附加可计算结构”。**方案主体不是报销系统**；`ledger` 只是第一个 strict 类型。

- **结构**：`ledger_accounts`（项目/账户、`limit_minor`、币种、额度版本 `effective_from/to`）+ `ledger` 类型的 entries（`kind=expense|reversal`、`amount_minor`、`currency`、`occurred_on`、`external_ref`）。
- **分单位**：金额一律整数分（`_minor`），禁止浮点。
- **不变量**：整数换算、冲正一对一、同币种、历史不可改金额、超额度不拒写但如实显示（沿用第 1 轮 INV-1…INV-10 中与记录层相关的条目）。
- **工具**：`ledger.balance(account_id, as_of?)` → `{limit, spent, reversed, remaining, basis, entries_considered[]}`。
- **示例场景**：额度 3000（`300000` 分），已报 160（`16000`）+1800（`180000`）→ 余额 `104000`；**隔 90 天再问，答案相同且能列出这两条 entry**（若记事本被清空记忆/记忆被改写，答案不受影响）。
- **与本提案的关系**：`ledger` 证明“需要可加总时可以加结构”，不是要求所有记录都带 schema。

### 7.2 目标测试（实现阶段）

- 不变量：`strict` 类型缺字段拒绝、`time_quality=unknown` 不被填成今天、`revision` 链完整。
- 幂等：同 key 同内容/不同内容两条路径。
- 检索：标签、时间窗、collection、关键词四路各有正例与**负例**（不得返回其他记录）。
- **隐私负控制（A 阶段必须）**：故意把 `private` 过滤去掉，S7、S7b 必须失败；三条查询入口（search / timeline / collection 列表）各一条用例。
- **凭据负控制（A 阶段必须，§5.12）**：①故意让回执回显明文 → S7c 必须失败；②故意让 `secret.use` 跳过用户确认 → S7d 必须失败；③故意让撤销后的 secret 仍可 `use` → S7e 必须失败；④故意允许任意目标工具接收值 → S7f 必须失败；⑤全流程扫描会话正文、工具回执、日志与 `notebook_entries`，断言明文与密文均不出现。
- **纠错负控制（A 阶段必须）**：故意让 `revise` 不写 revision、`delete` 仍被默认检索返回，S4/S5a/S5b 必须失败。
- **阶段不可单独开放**：断言 A 的“写入 + 纠错 + 隐私”三组用例必须在同一分支同时存在，缺任何一组则该阶段不得开放给用户（CI 或发布检查项）。
- 端到端：隔离 `--test-mode` 宿主 + 确定性模型；**A 阶段跑 A 门禁 15 条**（S1–S7、S7b、S7c–S7f、S9、S12），P2 追加 S9 的类型细分，P3 追加 S8，P1+ 追加 S10/S11。
- **“不依赖记忆”控制**（A）：清空 `memory.sqlite3` 后跑 S3，结果不变；S8 的同类控制在 P3 一并做。

| P5（可选） | 多端、导入、富文本 | Q6、Q7 | 是（增量） |

### 8.2 P0 / P1 不得单独交付（关闭 finding ①）

**硬约束**：原 P0（写入/检索/目录创建）与 P1（纠正/删除/整理/目录改名归档）**必须共同交付**，任何一方单独合并都不得对用户开放（可以合并在同一个 PR，也可以分两个 PR 但 A 的两条腿都绿之后才开入口）。

理由：模型可以自动建目录（Q1 的 B 选项）并写入记录，如果用户既不能改也不能删，**错误内容一旦进入就是永久的**——这违反 [产品方向](../../../docs/product/vision.md) 的“可纠正”承诺（记忆与个性化要求有来源、范围、时间与**纠正**）。

**A 阶段必须包含的最小纠错集**（即原 P1 的核心，不含“模型建议目录”这类增强）：

| 能力 | 工具 | 对应场景 |
| --- | --- | --- |
| 改内容 | `notebook.entry.revise(entry_id, patch, reason)` → 写 revision | S4 |
| 撤销/作废 | `notebook.entry.reverse(entry_id, reason)` | S5a |
| 删除 | `notebook.entry.delete(entry_id, reason)`（软删除；彻底删除见 Q8） | S5b |
| 改归属 | `notebook.entry.move(entry_id, collection_id)` | S10 |
| 整理目录 | `notebook.collection.rename/archive` | S11 |

**明确不做**（留在 P1 之后的增强）：`entry.merge`（重复合并）、模型主动建议目录、批量整理。它们可以单独合入，但**不阻塞也不太晚于** A 开放。

### 8.3 敏感标记与默认过滤进入 A（关闭 finding ②）

§5.8 承诺“默认检索不含 `private`”。如果 Sensitive 只在 P4 生效，A 阶段就已把写入与搜索开放给用户，承诺即落空。因此：

| 项 | A 阶段要求 | 后续阶段 |
| --- | --- | --- |
| 识别（规则 + 模型显式标记） | **必须** | — |
| 存放（`sensitivity` 字段 + 不进入记忆召回） | **必须** | — |
| 检索（默认结果不含 `private`，需当次明确要求） | **必须** | — |
| `notebook.entry.get` 对私密条目的可见性 | **必须**与 §5.10 既有权限语义一致（不新增渠道规则） | — |
| 导出默认排除私密 | — | P4（导出功能本身在 P4） |
| 渠道差异化 | — | P4，且只能用户显式开启 |

**若 Q5 最终选择“都不做标记”**，则必须**同时**把 §5.8 的隐私承诺降级改写（例如在 A 阶段明确声明“记事本内容与普通记录同等对待，用户需自行判断是否记录敏感信息”），并在 PR 中写明理由——**不允许代码与承诺不一致**。

### 8.4 门槛修正（保留第 3 轮结论）

ledger 细节（Q3）与数据位置/索引实现**不进入 A 的门槛**。数据位置与索引策略由工程师在实现 PR 中给出实测依据后收敛，提案阶段只保留约束（同库优先、迁移可回滚）。A 的门槛从“Q1、Q2”扩展为“**Q1、Q2、Q5**”——Q5 是隐私承诺的前置问题，但仍**只需回答 A/B/C 中的一个态度**，不是实现细节评审。

**建议顺序**：A（随手记 + 目录 + 纠正 + 隐私最小集）→ P2 类型化 → P3 账本（仅确有需求时）→ P4 导出/渠道。

## 9. 为什么不以记忆/向量检索为主路径

| 维度 | 记忆 + 召回（含向量） | 事件存储 |
| --- | --- | --- |
| 写入时机 | 维护流水线（活动投影 → 规则 → 可选语义整理），用户一句话不一定落库 | 用户/模型显式写入，立即持久 |
| 内容稳定性 | 语义整理会**改写**正文（`max_calls_per_hour=24`、`max_tokens_per_day=60000` 预算内） | 正文只经显式 revise 变更，历史保存在 revisions |
| 生命周期 | `working` 有 TTL（默认 86400 秒）；召回按预算截断 | 长期保存，无 TTL |
| 检索方式 | 按当前问题相似度取前 k，**结果不稳定** | 标签/时间/目录/全文，结果稳定可复现 |
| 可审计 | 难以回答“参与了哪些条目” | 每条记录、每次修改都有 id 与审计 |
| 可计算 | 模型心算不可靠 | 类型工具确定性计算 |
| 失效模式 | 静默错误（答得像、依据不存在） | 显式错误（找不到就追问） |

**结论**：用户“不能用传统记忆/向量检索”的判断成立。两者是**分工**而非替代——
- **记忆**：关于“我”的经历、偏好、约定；需要随时间被模型整理与推断。
- **事件存储**：关于“事与物”的原始记录；需要原样保留、可查、可算、可纠。
- 允许**弱连接**：查询记事本时可以把“相关记忆”作为补充提示，但**不能**作为金额/事实的唯一依据。本提案不改变现有记忆系统的任何行为。

### 10.1 A 阶段门槛（首次开放前必须回答）

**Q1 目录（collection）自由度 — 已决定（2026-11-02）：B**
- 选项：A. 模型发现同主题 ≥3 条时**建议**创建，用户确认后建；B. 模型可直接建 `auto_created` 目录，事后可归档（**已选**）；C. 只能由用户明确要求创建。
- 影响：目录是“自己长出来”还是“始终由用户掌控”；B 最省事但可能杂乱，C 最可控但用户要自己分类。
- 决策：采用 B。模型可自动创建 `auto_created` 目录；必须可归档/改名/移动，且在回执中说明创建了哪个目录。

- 决策：不强制每条先选类型；默认按自由文本 `note` 记录，模型可根据内容自行决定/建议 `type`、`props_json`、tags，并在回执中给出轻提示。保留类型挂载点，供后续 `ledger`/`strict` 扩展；不要求用户逐条选类型。

**Q5 敏感内容态度 — 已决定（2026-11-08）：A**
- 选项：A. 按 §5.8 做规则 + 模型打标，`sensitivity` 影响默认检索与导出，桌面与微信一致（**已选**）；B. 只靠用户手动标 `private`，不自动识别；C. 不做标记。

### 11.1 凭据存储威胁模型（§5.12）

| 威胁 | 攻击面 | 对策（A 阶段） | 残余风险（如实说明） |
| --- | --- | --- | --- |
| 本地磁盘/RAM 窃取 | `product.sqlite3` 被复制 | 只存信封密文；kek 在 OS 密钥库，复制数据库到其他用户/机器后无法解密（同 DPAPI 现状） | 同一用户下运行的恶意进程可调用 DPAPI 解密——**不承诺抵御同用户恶意软件** |
| 备份泄漏 | 产品库备份产物 | 备份只含密文；导出（P4）默认不含 `notebook_secrets` | 备份中的密文在 kek 仍有效时可被同一用户解密 |
| 模型/上下文泄漏 | 工具回执、会话正文、日志 | 回执只有 `secret_id/label/masked/fingerprint`；明文不进上下文；写入前扫描并拦截复述 | 用户自己把明文贴进对话时，已在会话中暴露，只能提示更换 |
| 越权使用 | 模型或第三方工具尝试取明文 | `secret.use` 需当次用户确认、绑定 `purpose`+`target_tool`、值只进执行层受控通道 | 用户误确认仍是可能路径（一次授权只作用于单次调用，影响有限） |
| 审计泄漏 | 审计表被读 | 审计只记 `secret_id/purpose/target_tool/at/actor/channel/receipt_id` | 审计本身可暴露“用过哪个密钥”，用户可接受 |
| 密钥轮换失效 | 仍能用旧值 | `rotate` 立即覆盖密文；`revoked_at` 后 `use` 立即失败 | 已注入到某次执行中的值无法追回（单次、短时） |
| 平台差异 | 非 Windows 平台没有 DPAPI | 走系统密钥库（Keychain/Secret Service）；不可用时 `secret.*` 整体返回 `unsupported`，**不降级为明文存储** | 该平台用户短期无法使用凭据存储 |

> 一句话边界：**本设计保证“明文不落库、不进模型上下文、取用需授权且可审计”，不保证“抵御同用户下的恶意进程或已被用户主动暴露的明文”。**
