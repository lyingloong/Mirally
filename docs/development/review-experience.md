# 审查经验库

> 由审查师维护的仓库级经验库。记录可复用、可检查的判断，不记录一次性任务细节或个人偏好。
>
> 更新：2026-11-01 · 状态：active · 所有者：审查师

## 使用方式

- **需求师**：拆分规格前阅读相关条目，避免设计出与既有约定冲突的方案。
- **工程师**：实现或修复前阅读相关条目；如果必须偏离，在 PR 说明理由。
- **审查师**：审查时核对相关条目；把新的可复用问题记为 candidate；定期去重、合并和退休。
- **队长**：在任务描述中带上本文件路径；每约 3 个已合并开发点，或出现重复模式时，安排一次“经验整理”任务。

本库不是任务规范的全部，也不替代任务级审查；它只回答“下一位工程师怎样少走同样的弯路”。

## 记录格式

每条经验使用稳定编号，至少包含：状态、适用范围、准则、反例/正例、来源。状态为 `candidate`、`active` 或 `retired`；退休条目保留，不静默删除。

候选先写入 `output/agent-workflow/experience-candidates.md`（gitignored）或 PR review comment；整理后再通过独立的 docs PR 更新本文件，不混入实现 PR。

```text
## EXP-CANDIDATE · 标题
- 来源 PR / 审查：
- 触发场景：
- 准则：
- 反例 / 正例：
- 适用范围：
- 建议状态：candidate
```

## 代码与实现准则

### EXP-0001 · 复用优先，不重复造轮子

- **状态**：active
- **适用范围**：需求、实现、审查
- **准则**：先查找现有模块、接口、工具、测试辅助和相似实现；新增抽象或 helper 前，说明现有实现为何不适用。重复实现必须是有意的取舍，并在 PR 中说明。
- **反例**：为新功能复制一份已有状态机或路径解析逻辑，只改名字。
- **正例**：扩展已有接口，或把可复用部分收敛到现有边界内。
- **来源**：用户 2026-11-01 提出的通用要求。

### EXP-0002 · 受限状态只保留一个正常准入入口

- **状态**：active
- **适用范围**：实现、审查、workflow 工具
- **准则**：进入 `specifying`、自动启动、合并等受限状态的正常路径只能有一个入口（如 `start`、`promote`、`resume`、`merge-approved`）；其他命令必须拒绝，或复用同一套容量/配额/用户优先/在飞上限校验。`--force` 只用于明确的恢复场景；满槽时登记等待，不靠放宽校验绕过。
- **反例**：`set-status` 直接把 `queued` 改成 `specifying`；`resume` 不检查并发槽位已被人占用；退回返工时直接增加活跃任务。
- **正例**：所有入口最终调用同一个准入函数；绕过时保留原状态并返回可操作错误；容量不足时进入等待队列，槽位释放后再恢复。
- **来源**：PR #3 审查 P2（2026-11-01），连续发现 promote/start、resume、set-status 三个旁路。

### EXP-0003 · 行为变更必须覆盖失败路径

- **状态**：active
- **适用范围**：实现、审查
- **准则**：除正常路径外，至少覆盖一个失败、边界或绕过路径；并发/状态机改动应覆盖“槽位已被占用”“重复进入”“权限/配额阻塞”等场景。
- **反例**：只断言成功返回值，不验证状态是否真的没有变化。
- **正例**：失败后断言原状态保留、错误可操作、没有产生重复任务或 PR。
- **来源**：PR #3 审查中多个可复现的并发旁路。

### EXP-0004 · 不绕过安全边界与人工闸门

- **状态**：active
- **适用范围**：需求、实现、审查
- **准则**：不绕过权限、配额、用户合并批准、路径校验和外部确认；异常时保留现场，不静默降级或假装成功。
- **反例**：为了“自动完成”跳过用户合并批准，或在配额失败后重建任务、重复开 PR。
- **正例**：阻塞时保留 worktree/分支/PR，记录阻塞原因，等条件恢复后继续。
- **来源**：工作流设计与 PR #3 审查。

### EXP-0005 · 文档里的命令必须可复制执行

- **状态**：active
- **适用范围**：实现、审查、文档
- **准则**：使用仓库相对路径或显式变量；不写开发机绝对路径；PowerShell 续行用反引号；说明主 checkout 与 worktree 的解释器差异。
- **反例**：把 `C:\Users\<name>\...` 写进示例，或从其他 worktree 直接运行不存在的 `.venv`。
- **正例**：`.\.venv\Scripts\python.exe tools\dev_workflow\agent_workflow.py ...`；worktree 先准备自己的环境或显式指定解释器。
- **来源**：PR #3 审查 P2（2026-11-01）。

## 工作流与协作准则

### EXP-0006 · 状态与文案必须真实、可操作

- **状态**：active
- **适用范围**：实现、审查、用户可见交互
- **准则**：处理中、成功、失败、未知必须区分；错误提示要给出下一步；同一场景保持用词一致；不添加重复或解释性冗余文案。
- **反例**：未确认成功就显示“已完成”，或所有失败都统一成“操作失败”。
- **正例**：失败时说明发生了什么、当前状态、用户下一步可以做什么。
- **来源**：Mirally 文案与交互规范，以及微信文字提示工作流需求。

### EXP-0007 · 小步、可审查、单一目标

- **状态**：active
- **适用范围**：实现、审查
- **准则**：一个 PR 围绕一个可审查目标；不做无关重构；经验库、流程文档等元信息更新放在独立 docs PR，不混进实现 PR。
- **反例**：顺手重构半个模块，或把经验总结塞进功能 PR。
- **正例**：实现 PR 只含目标改动、测试和必要的用户文档；经验候选先本地记录，整理后单独提 PR。
- **来源**：工作流设计。

## 维护规则

1. **只收可复用判断**：有来源、有触发场景、能帮助下一位工程师做决定；任务细节、个人偏好和无法执行的空话不收。
2. **去重优先**：新条目先搜索已有条目；能合并就合并，不堆近义准则。
3. **保持短小**：如果一条准则不能改变下一个实现或审查决定，就删除、合并或退休。
4. **定期整理**：每约 3 个已合并开发点，或出现重复模式时，审查师执行一次整理；更新本文件日期并走 docs PR。
5. **状态可追溯**：`retired` 条目保留并注明原因；不要用删除来掩盖旧结论。
6. **不替代审查**：本库是辅助，不降低当前 PR 的行为、安全和体验审查要求。
